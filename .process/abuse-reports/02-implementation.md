### Stated plainly: what is NOT covered

**The step-4 `CountAsync` predicate is not constrained by any test.** `_reportRepository.CountAsync(...)` is an NSubstitute stub matched on `Arg.Any<Expression<Func<Report, bool>>?>()`; NSubstitute never invokes the expression. If `x.ItemType == request.ItemType && x.ItemId == request.ItemId` were replaced with `x => true`, or with the wrong item's id, **every test would still pass**. The cap is therefore proven to *fire at the right threshold* (test 12 + mutation 1) but its *scoping to the reported item* is unproven by unit tests. The same is true of the `GetByIdAsync` stubs. No test here claims otherwise.

### Wire-level checks (things no unit test can see)

Ran the API (`ASPNETCORE_ENVIRONMENT=Development`, `https://localhost:62935`) against the local SQL Server, then killed it.

- **Anonymous** `POST /api/reports` → `200`, body `{"id":"e03e8717-…","status":"Open","createdAt":"2026-09-05T01:13:11.0004496+03:00"}` — camelCase, as the one-JSON-contract rule requires.
- **Bearer-carrying** `POST /api/reports` (JWT minted with the configured `CoreJwt` key; sanity-checked first against `GET /api/auth/me` → 200 for the real user) → `200`.
- **Decision 8 confirmed against the database**, which is the only place it is observable:

| Id | ItemType | Reason | Status | ReporterUserId | CreatedBy |
|---|---|---|---|---|---|
| E03E8717… | Engineer | Malicious | Open | (null) | (null) |
| 81FA7F4C… | Engineer | Other | Open | 57E40D05-ADBC-4C97-9DA2-6828405F8DA0 | 57E40D05-…-6828405F8DA0 |
| ADCA8671… | Engineer | Spam | Open | (null) | (null) |

  The bearer request stored a real `ReporterUserId` **and** `CreatedBy`. With class-level `[Authorize]`, `AuthorizationMiddleware` populates `HttpContext.User` even though the action is `[AllowAnonymous]`. The anonymous request stored NULL, not `Guid.Empty`.
- **Status-agnostic lookup**: created a `Draft` engineer via the API, reported it anonymously → `200` with a byte-identical response shape to the Published case, then deleted the draft (`204`). Draft and Published are indistinguishable from the response.
- **400 path**: `itemId` = a random unknown Guid → `HTTP 400`, `{"code":"REPORT_ITEM_NOT_FOUND","message":"We couldn't find the item you are reporting."}`.
- **422 paths**: `itemId` = all-zeros → `422 REPORT_ITEM_ID_REQUIRED`; `reason: "Other"` with `details: "   "` → `422 REPORT_DETAILS_REQUIRED`. Both resx lookups resolved to English prose, so the resource keys are wired.

## Notes for review

1. **`SubmitReportHandlerTests.cs` is 129 lines**, over the ~100-line rule, after I had already compacted it from 138. Six handler tests with a 3-line AAA body each plus 14 `using` lines and the substitute block does not fit in 100. I did **not** split it, because the plan fixes tests 4–9 to the class name `SubmitReportHandlerTests` and my contract is to match the plan's class and method names exactly. If you would rather have the split, it needs a new class name and that is your call, not mine.
2. **The Postman example body can never return 200.** The plan prescribes `"itemId": "00000000-0000-0000-0000-000000000000"` verbatim and I shipped it verbatim — but I confirmed on the wire that `Guid.Empty` is rejected by the validator first, so the request as-shipped returns `422 REPORT_ITEM_ID_REQUIRED`, never reaching the handler. It documents the contract but does not demonstrate the endpoint. Swapping in a real catalog id would make it a working example; I did not do that unilaterally.
3. **Three real rows are now in the local dev `Reports` table** (listed above) from the wire checks. I left them deliberately — they are the evidence for Decision 8 and I did not want to destroy it. Delete them with `DELETE FROM Reports;` if you want a clean local DB. The `wire-check-draft` engineer I created was soft-deleted via the API.
4. **I did not run the Decision 8 counterfactual.** I wanted to temporarily flip the controller to a bare `[AllowAnonymous]`, re-POST with a bearer, and show `ReporterUserId` coming back NULL — the direct proof of the plan's claim. The permission classifier blocked the edit (it reads as weakening auth, fairly), and I chose not to route around the denial. The positive direction is proven above and the definition of done only asks for that, but the counterfactual remains unverified. If you want it, it is a two-minute check with your own hands.
5. **`Program.cs` was not touched.** The plan does not ask for it, `[Authorize]` needs no registration, and `AddControllers().AddJsonOptions(JsonStringEnumConverter)` was already present — which is why `"reason":"Malicious"` binds. Confirmed on the wire rather than assumed.
6. **Validator rule ordering**: `Details` max-length runs before the `Other`-requires-details rule, per the plan's table. A whitespace-only `Details` with `Reason = Other` therefore returns `REPORT_DETAILS_REQUIRED` (FluentValidation's `NotEmpty`, which `ValidateRequired` wraps, treats whitespace as empty). Test 19 covers `null`, `""` and `"   "`.
7. **The local DB was two migrations behind** when I ran `database update` — it also applied `scan003`. Unrelated to this slice, just noting it in case the state surprises you.
